## [2026-08-12] — db2 (второй склад) — OUT of scope для кросс-табличных отчётов v1

**Scope:** Feature #27 (Отчёт «Движение товара»); принцип применяется ко всем будущим кросс-табличным отчётам.

**Решение:** Единые отчёты, объединяющие несколько таблиц через `UNION`, в v1 работают **только** с основной БД (`Yii::$app->db`). Таблицы, привязанные к `Yii::$app->db2` (`Arrival2`, `ReturnArrival2`), не включаются в UNION.

**Причина:**
1. Yii2 `Query` привязан к одному `Connection` — SQL-level `UNION` между `db` и `db2` невозможен (разные серверы).
2. PHP-merge двух result set'ов ломает пагинацию `DataProvider` и рискует OOM на больших объёмах.
3. `config/db2.php` в текущей установке пуст (dsn=`mysql:host=;dbname=`) → второй склад фактически не сконфигурирован.
4. MVP-принцип: сначала базовая функциональность, расширение на db2 — отдельная feature.

**Последствия:**
- Все новые search-модели с UNION используют только основную БД.
- Sell2 (таблица в **основной** БД, не путать с `Yii::$app->db2`) — включается, т.к. это черновики/отложенные продажи, ставшие sold=1.
- Когда/если понадобится db2 — открывать отдельную feature "v2: cross-DB отчёты" с решением через MySQL FEDERATED, репликацию или PHP-merge с осознанным ограничением пагинации.

## [2026-08-12] — Immutable event log для операций с удалением исходной записи

**Scope:** Feature #27 (sverka_log); паттерн применим ко всем будущим случаям, где применение операции удаляет исходную запись.

**Решение:** Если бизнес-логика удаляет исходную запись сразу после применения (как `Sverka` в `SverkaController::actionReceived`), а история операций нужна для отчётов — заводится отдельная таблица `*_log` (например `sverka_log`), в которую пишется snapshot **перед** удалением.

**Причина:**
- Не трогаем существующую логику применения — минимальный риск регрессии для критичных операций.
- Разделение ответственности: рабочая таблица — «черновик» (rebuild-able), log — immutable event stream.
- mysqldump backup (уже есть в `SverkaController::backupDatabase`) не заменяет структурированную историю для точечных запросов.

**Последствия:**
- Ретроспективные данные (операции ДО внедрения лога) восстановить нельзя — это документируется явно в issue как "out of scope".
- Log-таблицы должны быть indexed по `(id_product, datetime)` или аналогичному ключу отчётов.
